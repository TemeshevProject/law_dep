## 1. Цель, задачи, показатели

### 1.1 Цель

Обеспечить, чтобы каждое подразделение подтверждало в SimBASE только элементы своей
компетенции по назначенному чек-листу, а договор не мог быть направлен на подпись при
незакрытом блокирующем замечании или непринятом остаточном риске (пп. 1.2, 3.6, 4.3.1 Правил).

### 1.2 Задачи

1. Реализовать раздельные чек-листы по ролям: согласующий видит короткий список своей
   компетенции вместо полного перечитывания договора.
2. Исключить формальное согласование: подтверждение общей кнопкой без заполнения
   обязательных пунктов недопустимо (п. 3.6 Правил).
3. Автоматизировать блокировку и снятие блокировки строго по статусам пунктов (п. 3.1).
4. Перевести повторяющиеся проверки в автоматические (БИН и статус контрагента, статус по НДС,
   налоговая задолженность, бюджетный лимит, арифметика сумм и НДС, совпадение версий).
5. Обеспечить доказуемость: кто, что, когда и на основании какой версии подтвердил.
6. Дать бизнес-владельцу данные для пересмотра чек-листов (п. 10.8) — статистику
   по пунктам, замечаниям и рискам.

### 1.3 Показатели (Приложение 8 Б Правил)

Реализуются как отчёты по договорному блоку:

| Показатель | Источник данных в решении |
|---|---|
| Срок от создания карточки до подписания | события карточки |
| Число кругов согласования и доля возвратов | переходы в статус «Требуется доработка» |
| Доля блокирующих замечаний | пункты в статусе «Требуется доработка» к общему числу |
| Доля принятых остаточных рисков | карточки риска с решением «Принять» |
| Просрочки контрольных задач | задачи исполнения с нарушением срока |
| Доля подписанных версий с расхождением | срабатывания проверки «подписанная ≠ согласованная» |
| Доля непереданных оригиналов | статусы оригинала по п. 9.2 |
| Срок закрытия договора | события закрытия карточки |
| Сквозные: обходы маршрута, изменения после согласования, незаполненные чек-листы, повторяющиеся риски | журнал действий и аналитика по пунктам |

### 1.4 Границы

- Маршрутизация определяется действующей Матрицей принятия решений и признаками карточки
  (п. 3.4, 4.2.1) — ТЗ её не переопределяет, а использует.
- Закупочный процесс не регулируется (п. 1.7): его результат — вход договорного процесса.
- Доверенности (раздел 5, Приложение 5) и корреспонденция (разделы 6–7, Приложение 6)
  реализуются той же механикой; в настоящем ТЗ детализирован договорный блок,
  отличия по ним указаны в разделе 12.

## 3. Статусы, блокировки и остаточный риск

### 3.1 Статусы пункта (п. 3.1 Правил)

| Статус | Условия выставления в системе | Системное последствие |
|---|---|---|
| Подтверждено | пункт проверен в пределах компетенции | маршрут продолжается |
| Не применимо | пункт объективно не относится к документу; обоснование обязательно | маршрут продолжается после указания причины |
| Требуется доработка | несоответствие, отсутствие сведений, необходимость корректировки | автоматическая блокировка направления на подпись |
| Остаточный риск | замечание не устранено или неустранимо; риск описан | блокировка до решения уполномоченного лица |

Требования к реализации:

1. Статус «согласовано с замечаниями» отсутствует в интерфейсе и в API (п. 3.1.1).
2. «Не применимо» без заполненного обоснования не сохраняется.
3. Перевод пункта в «Остаточный риск» автоматически создаёт карточку риска
   с полями Приложения 7 и не позволяет продолжить маршрут до решения.
4. Завершение чек-листа подразделением невозможно, пока есть пункты без статуса:
   нажатие общей кнопки согласования при незаполненных обязательных пунктах отклоняется
   на стороне сервера (п. 3.6).
5. Снятие статуса «Требуется доработка» выполняет только автор замечания (п. 8.3);
   инициатор и создатель карточки не могут изменять результат чужого чек-листа (п. 3.5).

### 3.2 Блокирующие критерии (Приложение 7 Правил)

Система реализует их как автоматические предусловия направления на подпись:

| Критерий | Реализация |
|---|---|
| Не пройден обязательный маршрут либо отсутствует подтверждение чек-листа | проверка полноты статусов по всем обязательным шаблонам |
| На подпись направлена версия, отличная от согласованной | сверка идентификатора и контрольной суммы версии |
| Не подтверждены полномочия подписанта | пункты `LAW-04`, `SGN-03` не в статусе «Подтверждено» |
| Не определены предмет, сторона, существенная сумма, срок или результат | проверка обязательных полей карточки и пунктов `INI` |
| Отсутствует подтверждение бюджета, оплаты, технической исполнимости, безопасности или compliance при применимости блока | отсутствие завершённого чек-листа применимой роли |
| Существенный неустранённый и непринятый правовой риск | процессная блокировка ДПВ |
| Отсутствует обязательное корпоративное решение или одобрение | пункт `LAW-05` |
| Подписанный документ не совпадает с согласованным | запрет перевода в статус действующего договора (п. 4.3.7) |

### 3.3 Процессная блокировка ДПВ (п. 8.2)

Отдельное действие роли ДПВ: блокировка карточки с обязательным указанием основания
из перечня п. 8.2. Снимается только ДПВ. Действует независимо от статусов пунктов
других подразделений.

### 3.4 Принятие остаточного риска (раздел 8, Приложение 7)

- Карточка риска содержит обязательные поля: документ и версия, инициатор, описание
  остаточного риска, возможные последствия, позиция профильного подразделения, позиция
  инициатора, меры снижения, рекомендация ДПВ, решение, лицо принявшее решение,
  дата и комментарий.
- Решение принимает CEO, если Матрицей принятия решений вопрос не отнесён к иному лицу
  или органу; в этом случае CEO направляет вопрос компетентному лицу через то же действие (п. 8.6).
- Принятие риска фиксируется отдельным действием в SimBASE; подписание без отражения
  решения в карточке не считается надлежащим принятием риска (п. 8.7).
- Решение действует только для указанной версии и раскрытых обстоятельств: существенное
  изменение документа аннулирует решение и требует повторной оценки (п. 8.9).
- Принятие риска не заменяет обязательные корпоративные одобрения и полномочия
  подписанта (п. 8.8) — соответствующие блокирующие критерии сохраняются.
- Неурегулированные разногласия между подразделениями до вынесения вопроса CEO
  рассматривает бизнес-владелец (п. 8.10): отдельный маршрут эскалации на ДПВ.

## 4. Функциональные требования

### FR-01. Конструктор шаблонов чек-листов

Администратор SimBASE по решению бизнес-владельца создаёт и версионирует шаблоны.
Атрибуты шаблона: код, наименование, роль, блок Приложения 3, обязательность,
правила применимости, разделы, порядок пунктов, статус (черновик / активен / архив), версия.
Изменение распределения ответственности, блокирующих критериев или обязательных статусов
выполняется только в порядке изменения ВНД и синхронно отражается в системе (п. 11.3):
публикация версии шаблона требует ссылки на решение бизнес-владельца.

### FR-02. Атрибуты пункта

| Атрибут | Назначение |
|---|---|
| `code` | стабильный код пункта (для аналитики, отчётности и ссылок в ВНД) |
| `title` | формулировка подтверждения |
| `hint` | критерий проверки, ссылка на пункт Правил или иного ВНД |
| `appendix3_block` | блок Приложения 3, который раскрывает пункт |
| `role_code` | ответственная роль |
| `applicability` | условие показа по признакам карточки |
| `na_allowed` | допустим ли статус «Не применимо» |
| `risk_allowed` | допустим ли перевод в «Остаточный риск» либо пункт устраним только доработкой |
| `evidence_required` | требуется ли вложение-доказательство |
| `auto_source` | источник автопроверки |
| `reset_on` | события существенного изменения, аннулирующие подтверждение (п. 3.2.2) |
| `default_assignee` | адресат замечания по умолчанию |

Пункты с `risk_allowed = false` — те, где Правила не допускают продолжения без устранения:
отсутствие полномочий подписанта, отсутствие обязательного корпоративного одобрения,
несовпадение версии, неопределённость предмета, стороны, суммы, срока или результата.

### FR-03. Правила применимости

Система показывает только применимые пункты (Приложение 3, преамбула). Признаки карточки
для условий (п. 3.4): вид документа, предмет, сумма и валюта, подписант, наличие технических
условий, наличие денежных обязательств, IP и ПО, данные и персональные данные,
конфиденциальность, участие государственных органов, проект ГЧП, государственные закупки,
филиал, резидентство контрагента, статус по НДС, режим налогообложения, наличие аванса,
наличие нескольких языковых версий, отступление от типовой формы, рамочный характер договора.

Условия задаются конструктором без программирования; каждое правило имеет владельца
и ссылку на решение бизнес-владельца.

### FR-04. Инстанцирование и заполнение

- Экземпляры чек-листов создаются при активации шага маршрута и являются снимком версии
  шаблона: последующее изменение шаблона не меняет активные экземпляры.
- Автопроверки рассчитываются при создании экземпляра и по кнопке «пересчитать»;
  результат содержит источник и время получения данных.
- Согласующий по каждому пункту выставляет статус, при необходимости прикладывает
  доказательство и ссылается на фрагмент версии документа.
- Переопределение автопроверки допускается с обязательным обоснованием и фиксируется
  в журнале как отдельное событие.
- Массовые действия допустимы только для пунктов с `na_allowed = true` и требуют
  общего обоснования; массовое «Подтверждено» не предусмотрено (п. 3.6).
- Делегирование технического действия не переносит ответственность: исполнитель
  отображается отдельно от ответственной роли (п. 2.2.1). Замещение — по официальному
  назначению (п. 2.2.2).

### FR-05. Завершение чек-листа подразделения

Завершение возможно, если все применимые пункты имеют один из четырёх статусов и
для статусов «Не применимо» и «Остаточный риск» заполнены обоснование и карточка риска.
Наличие хотя бы одного пункта «Требуется доработка» переводит карточку в блокировку и
направляет замечания инициатору с фиксацией автора, пункта и версии.

### FR-06. Версии и аннулирование подтверждений (пп. 3.2.1–3.2.3)

1. Каждое подтверждение привязано к версии файла; система фиксирует наименование файла,
   дату загрузки и автора изменения.
2. При изменении предмета, цены, сроков, объёма, порядка оплаты, ответственности,
   приложений либо иного существенного условия подтверждения затронутых подразделений
   аннулируются автоматически по правилам `reset_on`.
3. Если затронутые подразделения невозможно определить автоматически, система назначает
   полный обязательный маршрут (п. 3.2.2) — поведение по умолчанию при неопределённости.
4. При повторном направлении обязательны: новая редакция в Word и, при доступности,
   файл сравнения версий; ответы инициатора фиксируются напротив каждого замечания (п. 3.2.3).
5. Локальная редакционная правка, не меняющая смысл и обязательства, подтверждается ДПВ
   без повторения полного маршрута, если характер изменения однозначно зафиксирован (п. 4.2.6):
   отдельное действие ДПВ «подтвердить редакционный характер правки» с обязательным описанием.

### FR-07. Замечания

Замечание всегда связано с пунктом, автором, версией документа и адресатом. Жизненный цикл:
создано → отработка инициатором → повторное направление → подтверждение устранения автором
замечания → снято. Альтернативные исходы: признано неприменимым с обоснованием;
оформлено как остаточный риск (п. 3.1.1). Закрытие замечания инициатором невозможно.

### FR-08. Допуск к подписанию и регистрация

- Кнопка направления на подпись недоступна при незавершённых обязательных блоках
  (Приложение 8 А) и при активной процессной блокировке ДПВ.
- Перед направлением фиксируется финальная версия; дальнейшая загрузка новой версии
  требует повторного допуска.
- После подписания система сверяет загруженный подписанный комплект с согласованной версией;
  при расхождении карточка не переводится в статус действующего договора (п. 4.3.7),
  создаётся замечание ДПВ.
- Внутренний регистрационный номер присваивается ДПВ либо формируется системой;
  дата подписанного договора при регистрации не изменяется (п. 4.3.6).
- Способ подписания (бумага, ЭЦП, согласованный сторонний сервис) и место хранения
  электронного подлинника фиксируются в карточке (п. 4.3.3).

### FR-09. Контрольные задачи исполнения (п. 4.4.1)

После регистрации система формирует задачи по сроку договора, поставке или оказанию услуг,
приёмке, оплате, закрывающим документам и ЭСФ, отчётности, гарантии, пролонгации и иным
существенным обязательствам. По каждой задаче: ответственный контролёр, срок, обязательный
вид подтверждения. Статус «исполнено» доступен только при наличии подтверждающего документа,
системного события либо мотивированного комментария (п. 3.2.4). Причина нарушения срока
фиксируется отдельно от факта просрочки (п. 4.4.4).

### FR-10. Закрытие договора (пп. 4.4.7, 4.4.8)

Закрытие возможно при подтверждении инициатором фактического исполнения и бухгалтерией
завершения расчётов, при отсутствии незавершённых задач и при учтённом статусе оригинала.
Незавершённые гарантийные, претензионные, конфиденциальные, лицензионные и иные
продолжающиеся обязательства не позволяют закрыть карточку полностью: по ним сохраняются
самостоятельные контрольные задачи.

### FR-11. Оригиналы и электронные подлинники (раздел 9)

Статусы бумажного оригинала: «ожидается», «получен инициатором», «передан в ДПВ»,
«временно выдан», «возвращён», «утрачен», «не формируется» (для последнего обязательно
основание электронной формы). Передача, временная выдача и возврат фиксируются с указанием
документа, даты, передающего, принимающего и цели. ДПВ получает отчёт о расхождениях между
ожидаемыми и фактически принятыми оригиналами (п. 9.5) с рассылкой инициаторам.

### FR-12. Уведомления

Уведомления по применимым событиям: назначение шага, поступление замечания, повторное
направление, приближение и наступление срока согласования, просрочка, создание карточки
риска, принятое решение по риску, окончание срока договора не позднее чем за 30 календарных
дней (п. 4.4.6), изменение ответственного, риск нарушения контрольного срока.

### FR-13. Права доступа

Заполнение чек-листа доступно только назначенной роли или её официальному замещающему.
Инициатор и создатель карточки не могут исключить обязательного согласующего, изменить
результат чужого чек-листа или закрыть незавершённое контрольное действие (п. 3.5).
Изменение маршрута — только администратором на основании зафиксированного решения
бизнес-владельца. Доступ к конфиденциальным документам и персональным данным — ролевой
(Приложение 8 А). Учётная запись персональна; подтверждение действий за другого работника
запрещено (п. 3.2.6) — технически исключается общий доступ к действиям подтверждения.

### FR-15. Аналитика и отчётность

Отчёты раздела 1.3, а также: частота замечаний по каждому пункту (основание для пересмотра
чек-листов по п. 10.8), длительность шагов по ролям, доля переопределённых автопроверок,
перечень повторяющихся остаточных рисков, обходы маршрута и изменения после согласования.
Экспорт реестров и данных для Процессного офиса (Приложение 8 А).

### FR-16. Журнал действий

Неизменяемый журнал: пользователь, дата и время, версия файла, содержание замечания,
результат проверки, решение о риске, изменение ответственного, подтверждение исполнения
(п. 3.2.5). Выгрузка «Лист согласования договора» в PDF с полным составом пунктов,
статусов, обоснований, авторов и версий — как доказательство прохождения процесса.

### FR-17. Работа при недоступности системы (п. 3.2.7)

Предусмотрен режим восстановления: действие, выполненное по письменному решению
Генерального директора при недоступности SimBASE, вносится в карточку задним числом
с обязательным приложением решения и отметкой «внесено при восстановлении»;
исходные дата и время события указываются отдельно от даты внесения.

## 5. Модель данных

```
ChecklistTemplate 1 ──< TemplateVersion 1 ──< ChecklistItem
  code, name, role_code,      version, status,        code, title, hint, section,
  appendix3_blocks,           published_at,           appendix3_block, applicability,
  is_mandatory, status        vnd_decision_ref        na_allowed, risk_allowed,
                                                      evidence_required, auto_source,
                                                      reset_on, default_assignee

ApprovalStep 1 ──< ChecklistInstance 1 ──< ItemConfirmation
                     template_version_id        item_code,
                     contract_id,               status ∈ {confirmed, not_applicable,
                     document_version_id,                  rework_required, residual_risk},
                     status, completed_at       justification, evidence[],
                                                confirmed_by, confirmed_at,
                                                is_auto, auto_snapshot, is_overridden

ItemConfirmation 1 ──< Remark          (замечание: автор, адресат, версия, статус, ответ)
ItemConfirmation 1 ──? RiskCard        (поля Приложения 7, решение, лицо, дата)
Contract         1 ──< ProcessBlock    (процессная блокировка ДПВ: основание, автор, снятие)
Contract         1 ──< ControlTask     (обязательство, контролёр, срок, вид подтверждения)
Contract         1 ──< OriginalRecord  (статус оригинала, держатель, передачи, возвраты)
*                1 ──< AuditEvent      (append-only)
```

Ключевые ограничения целостности:

- `ItemConfirmation` со статусом `not_applicable` требует непустого `justification`;
  со статусом `residual_risk` — связанной `RiskCard`.
- Статус `residual_risk` не сохраняется для пунктов с `risk_allowed = false`.
- Экземпляр хранит копию формулировок пунктов на момент создания — лист согласования
  должен быть воспроизводим спустя годы.
- Подтверждения не удаляются: изменение статуса создаёт новую запись и событие аудита.

## 7. Требования к интерфейсу

1. Чек-лист открывается рядом с версией документа: переключение контекста не требуется.
2. Постоянно видны: число пунктов по статусам, наличие блокировки, причина недоступности
   кнопки завершения.
3. Выбор статуса — одно действие; обоснование и вложение запрашиваются сразу, когда
   обязательны по атрибутам пункта.
4. Пункты сгруппированы по разделам шаблона; критерий проверки раскрывается по пункту.
5. Автопроверки визуально отличаются: показаны значение, источник, время получения,
   кнопка пересчёта; переопределение требует обоснования.
6. При повторном направлении согласующему показываются: изменившиеся поля карточки,
   файл сравнения версий и список аннулированных подтверждений, требующих перепроверки.
7. Инициатору доступна сводная страница всех замечаний по договору с группировкой
   по подразделениям и полем ответа напротив каждого замечания.
8. Карточка риска заполняется по форме Приложения 7 без свободного формата.
9. Язык интерфейса — русский и казахский; форматы даты и сумм — локальные.
10. Просмотр и подтверждение доступны с планшета для подписанта и руководителей.

## 8. Нефункциональные требования

- Открытие экземпляра чек-листа (до 60 пунктов) — не более 1,5 с на 95-м перцентиле.
- Автопроверки выполняются асинхронно; недоступность внешнего источника не блокирует
  ручное заполнение.
- Хранение журнала и листов согласования — по срокам утверждённой номенклатуры дел (п. 9.12).
- Ролевой доступ к конфиденциальным документам и персональным данным; обработка
  персональных данных — по законодательству Республики Казахстан о персональных данных.
- Все изменения шаблонов версионируются со ссылкой на решение бизнес-владельца
  и допускают откат.

## 9. Внедрение (п. 11.2 Правил)

1. **Электронная форма без автоблокировок.** До ввода всех автоматических блокировок
   участники заполняют чек-листы в доступной электронной форме; собирается статистика
   по срабатываниям и формулировкам.
2. **Пилот** на договорах с наибольшим объёмом: ДПВ, Финансы, Бухгалтерия на одном виде
   договора (услуги с резидентом, плательщиком НДС, без аванса, без ПДн и IP).
3. **Включение автоблокировок** по критериям Приложения 7 и перевод остаточных рисков
   в отдельное действие CEO.
4. **Полный охват** ролей и видов договоров, затем доверенности и корреспонденция.

Критерий перехода между этапами: отсутствие роста срока согласования и доля пунктов,
переведённых в «Требуется доработка» по формальным причинам, ниже 5 %.

|---|---|---|

| AC-15 | Попытка закрыть договор при незавершённой гарантийной задаче | Закрытие недоступно (п. 4.4.8) |

Приложения 8 Б; процессная блокировка ДПВ как отдельное действие.

**Этап 3.** Доверенности и корреспонденция на том же механизме, кадровый триггер
по доверенностям, сравнение версий с подсветкой отклонений от типовой формы,
предзаполнение пунктов на основе статистики замечаний.

Зависимости: автопроверки этапа 2 требуют стабильных кодов пунктов этапа 1;
аналитика для пересмотра чек-листов (п. 10.8) требует накопленных данных этапа 2.

## 12. Доверенности и корреспонденция (за границами детализации)

Механизм тот же: шаблон по роли, четыре статуса, блокировка, привязка к версии.
Отличия, которые нужно учесть при переходе к этим блокам:

- **Доверенности** (раздел 5, Приложение 5): чек-листы для инициатора, ДПВ, Финансов
  (денежные полномочия), доверителя; кадровый триггер проверки действующих доверенностей
  при увольнении, переводе, изменении функции и прекращении временного исполнения
  обязанностей; учёт выдачи и возврата бумажного оригинала; уведомления об окончании срока
  за 30 календарных дней и повторно; закрытие карточки только после фиксации основания
  прекращения, статуса оригинала и направленных уведомлений.
- **Корреспонденция** (разделы 6–7, Приложение 6): регистрация в Documentolog при
  ведении процесса в SimBASE, роль Офис-регистратора, внешний срок ответа, обязательное
  направление документов с существенным последствием CEO и ДПВ, связь входящего письма
  с ответом и всей цепочкой, обязательное согласование ДПВ по признакам п. 7.1.5,
  подтверждение отправки.

## 13. Риски реализации

| Риск | Мера |
|---|---|
| Формальное подтверждение пунктов «не читая» | короткие ролевые чек-листы, обязательные доказательства по ключевым пунктам, аналитика пунктов без замечаний за период как основание для пересмотра (п. 10.8) |
| Избыточные блокировки и остановка процесса | этап без автоблокировок, разделение `risk_allowed` и неустранимых пунктов, эскалация к бизнес-владельцу (п. 8.10) |
| Дублирование проверок между подразделениями | матрица «блок Приложения 3 → роль → пункт», запрет одинаковых пунктов у двух ролей без обоснования |
| Обход маршрута и правка после согласования | запрет изменения чужих пунктов, сверка версий, показатели обходов в отчётности |
| Аннулирование подтверждений при мелких правках приводит к лишним кругам | действие ДПВ по п. 4.2.6 с обязательной фиксацией характера правки |
| Недоступность внешних источников | деградация в ручной режим, кэш и снимки ответов |
| Расхождение между ВНД и настройками систем | публикация версии шаблона только со ссылкой на решение бизнес-владельца (п. 11.3) |

## 14. Открытые вопросы

Незаполненные значения в самих Правилах (в тексте обозначены как `________`), которые нужны
для настройки системы:

1. Срок восстановления карточки и журнала после восстановления доступа к системе (п. 3.2.7).
2. Срок загрузки полностью подписанной версии в SimBASE с даты подписания (п. 4.3.5).
3. Срок устранения расхождения по непереданным бумажным оригиналам после уведомления (п. 9.6).
4. Повторный срок уведомления об окончании доверенности (п. 5.3.1).
5. Ответственный за передачу в SimBASE кадровых событий и срок передачи (п. 5.3.3).
6. Ответственный за уведомление лиц, которым предъявлялась отзываемая доверенность (п. 5.3.5).
7. Срок возврата бумажного оригинала доверенности (п. 5.3.6).
8. Срок предоставления материалов соисполнителями по входящей корреспонденции (п. 6.2.4).
9. Ответственность ролей, оставленных незаполненными в Приложении 2: Администратор SimBASE,
   Администратор Documentolog, Контролёр исполнения входящей корреспонденции.
10. Ответственные за регистрацию исходящего письма, централизованный контроль исполнения
    и учёт оригиналов входящих писем (Приложение 6).

Требуют решения бизнес-владельца для настройки договорных чек-листов:

11. Пороговые значения: сумма, при которой подключаются Compliance и расширенная проверка
    контрагента; доля аванса, требующая обеспечения; сумма, требующая финансовой модели
    и проверки платёжеспособности; лимиты подписантов по Матрице принятия решений.
12. Перечень пунктов, по которым остаточный риск недопустим в принципе
    (предложение приведено в FR-02, требует утверждения).
13. Сроки согласования по подразделениям и приоритет срока правовой экспертизы
    (по аналогии с п. 7.1.8 для писем).
14. Доступные к интеграции источники: сервисы КГД МФ РК, ГБД «Юридические лица»,
   судебный кабинет, санкционные перечни, кадровая система, бюджетный контур.
15. Нужна ли ЭЦП согласующего под чек-листом или достаточно записи в неизменяемом журнале.
16. Реестр утверждённых типовых форм договоров и порядок фиксации отступлений (п. 4.1.3).
