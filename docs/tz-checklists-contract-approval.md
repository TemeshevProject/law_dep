## 1. Цель и задачи

### 1.1 Цель

Встроить в процесс согласования договоров в SimBase механизм ролевых чек-листов: каждый участник
маршрута согласования видит и подтверждает только те пункты, которые относятся к его зоне
ответственности, а не перечитывает договор целиком.

### 1.2 Задачи

1. Сократить время согласования за счёт того, что согласующий работает по короткому
   структурированному списку вместо свободного чтения всего документа.
2. Снизить число возвратов «по кругу»: ошибки фиксируются как формализованные замечания
   с однозначным адресатом и критерием закрытия.
3. Обеспечить прослеживаемость: по каждому договору видно, кто что проверил, когда, с каким
   результатом и на основании каких документов.
4. Перевести повторяющиеся проверки в автоматические (реквизиты, ЕГРЮЛ, лимит бюджета,
   арифметика сумм и НДС), оставив человеку только содержательные решения.
5. Накопить статистику типовых нарушений, чтобы дорабатывать типовые формы договоров
   и убирать причины замечаний на входе.

### 1.3 Метрики успеха

| Метрика | Как считаем | Целевое значение |
|---|---|---|
| Время согласования (медиана) | от постановки на согласование до финального одобрения | −30 % к базовому периоду |
| Доля договоров с повторным кругом согласования | договоры с ≥2 возвратами инициатору / все договоры | −50 % |
| Доля шагов, закрытых без замечаний с первого раза | шаги без замечаний / все шаги | ≥ 70 % |
| Доля автоматически заполненных пунктов | автопункты / все пункты чек-листов | ≥ 25 % на MVP |
| Полнота комплекта на входе | договоры, прошедшие чек-лист инициатора без доборов документов | ≥ 85 % |

### 1.4 Границы (что не входит)

- Переработка самого маршрута согласования и матрицы полномочий — используется существующий
  механизм SimBase, чек-листы к нему пристраиваются.
- Автоматический семантический анализ текста договора (NLP-извлечение условий) — вне MVP,
  задел описан в разделе 12.
- Электронная подпись и обмен с контрагентом — существующая функциональность, чек-лист
  только фиксирует факты.

## 2. Термины

| Термин | Значение |
|---|---|
| Договор | Карточка договора в SimBase: реквизиты, файлы, версии, маршрут согласования |

| Шаг согласования | Задача конкретного согласующего в рамках маршрута |

| Экземпляр чек-листа | Копия шаблона, созданная для конкретного шага конкретного договора |

| Замечание | Зафиксированное несоответствие по пункту с адресатом и жизненным циклом до закрытия |
| Автопроверка | Пункт, значение которого система вычисляет из данных SimBase или внешнего источника |

## 3. Общая логика решения

```
Карточка договора (версия N)
        │
        ├─ запуск маршрута согласования
        │
        ▼
для каждого шага маршрута:
   роль шага ──► подбор шаблонов чек-листов по правилам применимости
                       (тип договора, сумма, валюта, резидентство контрагента,
                        наличие аванса, ПДн, ИС, лицензируемая деятельность…)
                       │
                       ▼
               создание экземпляра чек-листа (снимок шаблона версии X)
                       │
                       ├─ автопункты заполняются системой
                       └─ остальные пункты заполняет согласующий
                       │
                       ▼
   завершение шага возможно, если:
        все обязательные пункты отвечены
        и нет открытых блокирующих несоответствий
                       │
        ┌──────────────┴───────────────┐
   «Согласовано»                  «На доработку»
   (в т.ч. с замечаниями,          (замечания → инициатору,
    не блокирующими)                шаг ждёт новой версии)
```

Ключевые принципы:

1. **Экземпляр — это снимок.** Изменение шаблона не меняет уже созданные экземпляры;
   в экземпляре хранится ссылка на версию шаблона.
2. **Роль определяет содержание.** Один шаг = одна роль = один или несколько применимых
   чек-листов (например, «Бухгалтер: базовый» + «Бухгалтер: ВЭД», если контрагент — нерезидент).
3. **Блокировка — только по существенным пунктам.** Уровень критичности задаётся в шаблоне,
   чтобы процесс не встал из-за формальностей.
4. **Ответ «Не применимо» разрешён**, но требует причины, если пункт блокирующий.
5. **История неизменяема.** Ответы и замечания не удаляются, а версионируются.

## 4. Роли и зоны ответственности

Ниже — рабочий перечень ролей, для которых подготовлены чек-листы. Полные чек-листы —
в Приложении А (`docs/checklists-by-role.md`).

| # | Роль | Зона ответственности (что проверяет) | Что НЕ проверяет |
|---|---|---|---|
| 1 | Инициатор (владелец договора) | комплектность пакета, соответствие потребности, корректность введённых данных карточки | правовую и налоговую квалификацию |
| 2 | Руководитель инициатора | обоснованность потребности, приоритет, отсутствие дублирования, готовность ресурсов | текст договора |
| 3 | Закупки | процедура выбора поставщика, коммерческие условия, конкурентность цены | юридические формулировки |
| 4 | Юрист | полная правовая экспертиза текста, правоспособность и полномочия, риски и ответственность | бюджет, лимиты, налоговый режим контрагента |
| 5 | Бухгалтер | реквизиты сторон и банковские реквизиты, налоговый режим контрагента, НДС, первичные документы | коммерческую целесообразность |
| 6 | Финансист / финансовый контролёр | бюджет и лимиты, график платежей, cash flow, авансы и обеспечение, валютный риск, TCO | текст правовых оговорок |
| 7 | Экономическая безопасность / комплаенс | проверка контрагента, бенефициары, санкции, аффилированность, антикоррупция, лицензии | финансовые расчёты |
| 8 | Информационная безопасность / защита данных | передача ПДн, поручение на обработку, доступ к инфраструктуре, требования ИБ и SLA по инцидентам | коммерческие условия |
| 9 | Технический эксперт / профильное подразделение | ТЗ и спецификация, критерии приёмки, SLA, совместимость, гарантия | правовые риски |
| 10 | Подписант | закрытость всех согласований, полномочия на подпись, корпоративные одобрения, идентичность финальной версии | детальные проверки |
| 11 | Администратор договоров / делопроизводитель | регистрация, комплектность подписанного пакета, хранение, передача в учётную систему, контрольные даты | содержание условий |

Матрица RACI по ключевым решениям (сокращённо): решение о заключении — A: подписант,
R: инициатор; правовые риски — R: юрист; налоговые последствия — R: бухгалтер;
финансовые условия и лимиты — R: финансист; надёжность контрагента — R: безопасность.

## 5. Функциональные требования

### 5.1 Конструктор шаблонов чек-листов (FR-01)

- Администратор (роль `checklist_admin`) создаёт и редактирует шаблоны в разделе
  «Настройки → Согласование → Чек-листы».
- Атрибуты шаблона: код, название, роль, описание, признак обязательности,
  правила применимости, порядок пунктов, статус (черновик / активен / архив), версия.
- Пункты группируются в разделы (например, у юриста: «Стороны», «Предмет», «Ответственность»,
  «Форма и техника»).
- Поддерживается копирование шаблона и создание новой версии с отображением различий.
- Валидация при публикации: у каждого пункта задан тип ответа, уровень критичности,
  формулировка; для автопунктов — источник данных.

### 5.2 Атрибуты пункта чек-листа (FR-02)

| Атрибут | Описание |
|---|---|
| `code` | Стабильный код пункта (для аналитики и миграций) |
| `title` | Формулировка проверки, сформулированная как проверяемое утверждение |
| `hint` | Критерий приёмки / как проверять, ссылка на регламент |
| `answer_type` | `yes_no_na`, `yes_no`, `value` (число/строка/дата), `select`, `auto` |
| `severity` | `blocking` (блокирует шаг), `major` (замечание обязательно к отработке), `info` |
| `required` | Обязателен ли ответ для завершения шага |
| `requires_comment_if` | Условие, при котором комментарий обязателен (`no`, `na`, `any`) |
| `requires_attachment_if` | Условие, при котором обязательно вложение (например, выписка ЕГРЮЛ) |
| `applicability` | Условия появления пункта (см. 5.3) |
| `auto_source` | Для `auto`: источник значения (поле карточки, интеграция, вычисление) |
| `on_fail_route_to` | Кому по умолчанию адресуется замечание (инициатор, закупки, другая роль) |
| `reset_on` | События, при которых ответ инвалидируется в новой версии (см. 5.6) |

### 5.3 Правила применимости (FR-03)

Чек-лист и отдельные пункты подбираются по условиям над данными карточки договора.
Минимальный набор атрибутов для условий:

- тип договора (поставка, услуги, подряд, аренда, лицензия/ИС, NDA, агентский, займ, ВЭД);
- сторона инициативы (наша форма / форма контрагента);
- сумма договора и валюта, наличие безлимитной/рамочной суммы;
- резидентство контрагента, страна;
- налоговый режим контрагента (ОСНО / УСН / НПД / ИП / патент);
- наличие аванса и его доля;
- срок действия, наличие автопролонгации;
- признаки: передача ПДн, создание результатов ИС, доступ к ИТ-инфраструктуре,
  работы на объектах компании, лицензируемая деятельность, закупка через процедуру;
- отклонение от типовой формы (есть/нет).

Условия задаются как выражения вида `contract.amount > 5000000 AND contract.advance_share > 0`
с UI-конструктором (без написания кода администратором).

### 5.4 Инстанцирование и заполнение (FR-04)

- При активации шага согласования система создаёт экземпляры применимых чек-листов
  и сразу рассчитывает автопункты.
- Чек-лист отображается панелью рядом с просмотром документа: пункт → ответ → комментарий →
  вложение; виден прогресс («12 из 18, блокирующих открыто: 2»).
- Согласующий может: ответить, приложить файл, сослаться на фрагмент документа/страницу,
  создать замечание, запросить уточнение у инициатора без возврата всего шага,
  делегировать чек-лист или отдельный раздел другому сотруднику.
- Массовые действия: «отметить раздел как соответствующий», «отметить неприменимые пункты»
  (с обязательной общей причиной). Для блокирующих пунктов массовое действие недоступно.
- Автопункты: значение показывается с источником и временем расчёта, есть кнопка «пересчитать»;
  согласующий может переопределить автоответ с обязательным комментарием (факт переопределения
  фиксируется в аудите).

### 5.5 Правила завершения шага (FR-05)

- «Согласовать» доступно, если: отвечены все `required` пункты и нет открытых несоответствий
  с `severity = blocking`.
- «Согласовать с замечаниями» доступно при наличии только `major`/`info` замечаний;
  замечания переходят в список отработки и не блокируют дальнейший маршрут.
- «Отправить на доработку» формирует список замечаний с адресатами и возвращает договор
  инициатору; шаг переходит в статус «ожидает новой версии».
- «Отказать» (для случаев принципиальной невозможности) — с обязательным обоснованием,
  останавливает маршрут и требует решения эскалацией.
- Система не даёт завершить шаг «пустым»: попытка согласовать без заполнения показывает
  список незакрытых пунктов.

### 5.6 Поведение при новой версии договора (FR-06)

При загрузке новой версии файла или изменении значимых полей карточки:

1. Ответы сохраняются, но пункты с признаком инвалидации сбрасываются в «требует
   перепроверки». Триггеры инвалидации задаются в шаблоне: `file_changed`,
   `amount_changed`, `counterparty_changed`, `payment_terms_changed`, `dates_changed`.
2. Согласующему показывается «дельта»: что изменилось в карточке и, если доступно сравнение
   файлов, изменённые разделы; повторно подтверждать нужно только сброшенные пункты.
3. История ответов по предыдущим версиям остаётся доступной и сопоставленной с версией.
4. Полный перезапуск чек-листа происходит при смене контрагента или типа договора.

### 5.7 Жизненный цикл замечания (FR-07)

`Создано → Передано адресату → В работе → Исправлено (с описанием) → Проверено автором
замечания → Закрыто` либо `Отклонено (с обоснованием) → Эскалация`.

Требования: замечание всегда связано с пунктом чек-листа и версией договора; у замечания есть
адресат, срок, уровень критичности; закрыть замечание может только автор или его руководитель
(или администратор процесса); при закрытии блокирующего замечания шаг автоматически
возвращается в работу согласующему.

### 5.8 Делегирование и замещение (FR-08)

- Делегирование чек-листа или раздела с сохранением ответственности исходной роли.
- Замещение на период отсутствия (правила уже существующие в SimBase — переиспользовать).
- Групповые шаги: чек-лист заполняется совместно, видно, кто ответил на какой пункт;
  завершение шага — по правилу «любой из группы» или «все» (настройка).

### 5.9 Аудит и история (FR-09)

Неизменяемый журнал: кто, когда, какой пункт, старое и новое значение, комментарий,
вложения, версия договора, версия шаблона, IP/сессия. Журнал доступен на карточке договора
и выгружается в PDF как «Лист согласования с чек-листами» — юридически значимый след
проверки, пригодный для аудита и споров.

### 5.10 Отчётность и аналитика (FR-10)

Дашборды и выгрузки:

- срок прохождения шага по ролям (медиана, 90-й перцентиль), очередь и просрочки;
- топ пунктов, по которым чаще всего возникают замечания (кандидаты на доработку
  типовой формы или на автоматизацию);
- доля договоров, согласованных с отклонениями от типовой формы, и какие именно отклонения;
- нагрузка по согласующим, доля делегирований;
- «качество входа»: сколько замечаний генерирует каждый инициатор/подразделение;
- эффективность автопроверок: сколько пунктов закрыто автоматически, сколько переопределено.

### 5.11 Уведомления, SLA и эскалации (FR-11)

- Уведомления: назначен шаг, поступило замечание, замечание исправлено, приближается/наступил
  срок SLA, шаг просрочен, договор согласован.
- SLA на шаг настраивается по роли и сумме договора; при просрочке — эскалация руководителю роли.
- Каналы: интерфейс SimBase, e-mail, при наличии — корпоративный мессенджер.
- Дайджест «мои открытые чек-листы и замечания» с настраиваемой периодичностью.

### 5.12 Права доступа (FR-12)

| Действие | Кто |
|---|---|
| Просмотр своего чек-листа | согласующий шага, его замещающий/делегат |
| Просмотр всех чек-листов договора | инициатор, юрист, подписант, администратор процесса, аудит |
| Заполнение | только назначенный на шаг (или делегат) |
| Изменение шаблонов | `checklist_admin` |
| Закрытие замечания | автор замечания, его руководитель, администратор процесса |
| Выгрузка аналитики | руководители ролей, администратор процесса |

Доступ к файлам договора остаётся по существующим правилам SimBase: чек-лист не расширяет
права на документ.

### 5.13 Интеграции (FR-13)

| Источник | Что даёт | Пункты, которые автоматизирует |
|---|---|---|
| ЕГРЮЛ/ЕГРИП (ФНС) | наименование, ОГРН/ИНН, адрес, руководитель, статус, ликвидация | сверка реквизитов, правоспособность, полномочия «по уставу» |
| Сервис проверки контрагентов | задолженность по налогам, массовый адрес/руководитель, численность, выручка | признаки технической компании, налоговая осмотрительность |
| Картотека арбитражных дел, ФССП, реестр банкротств | судебные споры, исполнительные производства | надёжность контрагента |
| Санкционные и иные перечни | вхождение контрагента/бенефициаров в списки | комплаенс-проверка |
| Реестр самозанятых (НПД) | статус плательщика НПД на дату | пункт бухгалтера по НПД |
| Бюджетная система / бюджет SimBase | бюджетная строка, лимит, свободный остаток | лимит и наличие бюджета |
| 1С (или учётная система) | карточка контрагента, банковские реквизиты, договоры | сверка реквизитов, дублирование договоров |
| ЭДО (оператор) | приглашение/статус роуминга | готовность к обмену документами |
| Реестр шаблонов договоров | эталонная форма и её версия | отклонения от типовой формы (сравнение) |

Требования к интеграциям: кэширование ответов с указанием времени получения, деградация
без блокировки процесса (при недоступности источника пункт переходит в ручной режим
с пометкой «автопроверка недоступна»), хранение доказательства проверки (снимок ответа).

### 5.14 Импорт/экспорт шаблонов (FR-14)

Шаблоны выгружаются и загружаются в YAML/JSON для версионирования вне системы, переноса
между контурами (тест → прод) и код-ревью изменений. Формат — см.
`docs/checklists/contract-approval-checklists.yaml`. При импорте: валидация схемы,
предпросмотр различий, создание новой версии шаблона без затрагивания активных экземпляров.

---

## 6. Модель данных

```
ChecklistTemplate            1 ──< ChecklistTemplateVersion 1 ──< ChecklistItem
    code, name, role_code            version, status,               code, title, hint,
    is_mandatory, status             published_at, author           answer_type, severity,
                                                                    required, section,
                                                                    applicability,
                                                                    auto_source, reset_on

ApprovalStep 1 ──< ChecklistInstance 1 ──< ChecklistAnswer
                      template_version_id      item_code, value, comment,
                      contract_id,             answered_by, answered_at,
                      contract_version,        is_auto, auto_source_snapshot,
                      status, completed_at     is_overridden, state

ChecklistAnswer 1 ──< Finding (замечание)
                         severity, assignee, due_at, status,
                         description, resolution, closed_by, closed_at

ChecklistAnswer 1 ──< Attachment
Any entity      1 ──< AuditEvent (append-only)
```

Статусы:

- `ChecklistInstance`: `pending` → `in_progress` → `completed` | `revalidation_required` | `cancelled`
- `ChecklistAnswer.state`: `unanswered` | `answered` | `revalidation_required` | `overridden`
- `Finding.status`: `open` | `assigned` | `in_progress` | `fixed` | `verified` | `closed` | `rejected` | `escalated`

Требования к хранению: ответы и замечания не удаляются физически; редактирование ответа
создаёт запись в аудите с прежним значением; экземпляр хранит копию формулировок пунктов
на момент создания, чтобы «Лист согласования» был воспроизводим спустя годы.

## 7. API (минимальный контур)

| Метод | Назначение |
|---|---|
| `GET /api/checklist-templates` | список шаблонов с фильтрами по роли и статусу |
| `POST /api/checklist-templates/{code}/versions` | создать/опубликовать версию шаблона |

Правила завершения шага и блокировки проверяются **на сервере**, а не только в UI.

## 8. Требования к интерфейсу

1. Чек-лист открывается в одном экране с документом (сплит-вью), без переключения контекста.
2. Всегда видны: прогресс, число открытых блокирующих пунктов, кнопка завершения
   с подсказкой, чего не хватает.
3. Фильтры: «только блокирующие», «только незаполненные», «только с замечаниями».
4. Пункт компактен: формулировка, ответ одним кликом, раскрывающийся критерий (`hint`),
   поле комментария и вложение по требованию.
5. Автопункты визуально отличаются, показывают источник и дату данных.
6. Замечание создаётся из пункта в два действия, с автоподстановкой адресата.
7. Инициатор видит сводную страницу «все замечания по договору» с группировкой по ролям
   и статусам — единый список работ на доработку.
8. Поддержка работы с планшета (просмотр и подтверждение для руководителей/подписанта).
9. Интерфейс на русском языке, даты и суммы в локальных форматах; поддержка тёмной темы —
   по стандарту SimBase.

---

## 9. Нефункциональные требования

- Открытие экземпляра чек-листа (до 60 пунктов) — не более 1,5 с при 95-м перцентиле.
- Расчёт автопунктов — асинхронно, с прогрессом; недоступность внешнего источника
  не блокирует заполнение вручную.
- Одновременная работа: до 200 активных согласующих без деградации.
- Хранение аудита — не менее срока хранения договора (по умолчанию 5 лет после окончания
  действия, настраивается).
- Разграничение доступа по существующей модели SimBase; вложения чек-листов наследуют
  политику конфиденциальности договора.
- Обработка ПДн в рамках чек-листов (например, данные подписантов) — в соответствии
  с внутренней политикой и 152-ФЗ.
- Все изменения шаблонов — с авторством и возможностью откатиться на прежнюю версию.

---

## 10. Внедрение

1. **Мягкий режим (shadow).** Чек-листы заполняются, но не блокируют согласование.
   Цель — собрать статистику и откалибровать формулировки и уровни критичности.
2. **Пилот** на двух ролях с наибольшим объёмом рутины — юрист и бухгалтер — на одном
   типе договора (например, услуги с резидентом на ОСНО).
3. **Расширение** на финансиста, безопасность, закупки; включение блокировок по пунктам,
   доказавшим свою значимость на этапе 1.
4. **Полный охват** ролей и типов договоров, включение SLA и эскалаций.
5. Обучение: короткая инструкция на роль (1 страница) и подсказки в интерфейсе;
   владелец процесса ведёт реестр изменений чек-листов.

Критерий перехода между этапами — отсутствие роста времени согласования и доля
«ложных» блокировок ниже 5 %.

## 11. Приёмочные критерии

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| AC-01 | Договор услуг, контрагент на УСН, аванс 50 % | Бухгалтеру подставлен пункт про формулировку «без НДС»; финансисту — пункты про аванс и обеспечение |
| AC-02 | Юрист пытается согласовать с открытым блокирующим пунктом | Кнопка недоступна, показан список незакрытых пунктов; серверный запрос также отклоняется |
| AC-03 | Не совпал ИНН в договоре и ЕГРЮЛ | Автопункт бухгалтера в состоянии «не соответствует», создано замечание инициатору |
| AC-04 | Загружена новая версия файла после согласования юриста | Пункты юриста с `reset_on: file_changed` переведены в «требует перепроверки», остальные сохранены; юристу показана дельта |
| AC-05 | Контрагент — нерезидент | Добавлены чек-листы ВЭД: валютный контроль, налоговый агент, Incoterms, применимое право |
| AC-06 | Согласование с замечаниями `major` | Маршрут продолжается, замечания попали в список отработки с адресатом и сроком |
| AC-07 | Внешний источник (ЕГРЮЛ) недоступен | Пункт переведён в ручной режим с пометкой, процесс не остановлен |
| AC-08 | Выгрузка листа согласования | PDF содержит все пункты, ответы, авторов, даты, версии договора и шаблонов |
| AC-09 | Изменение шаблона во время активного согласования | Активные экземпляры не изменились; новые создаются по новой версии |
| AC-10 | Делегирование чек-листа | Делегат заполняет, в аудите видны и делегат, и исходный ответственный |

## 12. Этапы реализации

**Этап 1 (MVP).** Конструктор шаблонов, правила применимости по типу договора и сумме,
экземпляры на шагах, типы ответов `yes_no_na`/`value`, блокирующие пункты, замечания
с базовым жизненным циклом, аудит, выгрузка листа согласования, чек-листы для ролей
юрист/бухгалтер/финансист/инициатор.

**Этап 2.** Автопункты и интеграции (ЕГРЮЛ, бюджет, 1С, реестр НПД), инвалидация по
новой версии с дельтой, делегирование и замещение, SLA и эскалации, остальные роли,
дашборды аналитики.

**Этап 3.** Импорт/экспорт шаблонов между контурами, сравнение с эталонной формой
(diff по тексту договора) с автоматической подсветкой отклонений, подсказки на основе
накопленной статистики замечаний, предзаполнение пунктов на основе извлечения условий
из текста.

Порядок этапов отражает зависимости: автоматизация (этап 2) требует стабильных кодов
пунктов из этапа 1; работа с текстом (этап 3) опирается на накопленную статистику этапа 2.

## 13. Риски и допущения

| Риск | Последствие | Мера |
|---|---|---|
| Чек-листы слишком длинные | согласующие проставляют «да» не читая, формализм | лимит 15–20 пунктов на роль на MVP, критичность вместо «всё блокирует», аналитика по пунктам без замечаний за период → удаление |
| Избыточные блокировки | процесс встаёт, обход через эскалации | старт в мягком режиме, включение блокировок по данным пилота |
| Дублирование проверок между ролями | двойная работа и споры о ответственности | матрица ролей (раздел 4) как источник истины, запрет одного и того же пункта в двух ролях без явного обоснования |
| Недоступность внешних источников | остановка автопунктов | деградация в ручной режим, кэш |
| Роли в SimBase не совпадают с ролями из исходного документа | переделка шаблонов | шаблоны — данные, а не код; сверка по разделу 14 до старта разработки |
| Изменение законодательства (НДС, ПДн, валютный контроль) | устаревание пунктов | владелец процесса + версионирование шаблонов и регулярный ревью |

## 14. Открытые вопросы (требуют исходного документа и решения владельца процесса)

1. **Доступ к документу.** Открыть папку Google Drive для чтения по ссылке либо выгрузить
   документ в репозиторий/во вложение. После этого — сверить перечень и названия ролей,
   чтобы `role_code` в шаблонах совпадали с ролями маршрута в SimBase.
2. Совпадают ли роли из документа с ролями маршрута согласования в SimBase один-в-один,
   или нужна таблица соответствия?
3. Выделены ли в отдельные роли налоговый специалист и валютный контроль, или это зона
   бухгалтера (в текущем черновике — зона бухгалтера)?
4. Пороговые значения: сумма для обязательного участия безопасности, доля аванса, требующая
   обеспечения, лимит полномочий подписанта, число альтернативных предложений для закупок.
5. Какие источники проверки контрагента уже закуплены и доступны по API?
6. SLA по ролям: какие сроки закреплены регламентом?
7. Нужна ли юридически значимая фиксация чек-листа подписью согласующего (УКЭП/простая ЭП),
   или достаточно записи в аудите?
8. Есть ли утверждённые типовые формы договоров и их реестр — для пункта «отклонения
   от типовой формы».
